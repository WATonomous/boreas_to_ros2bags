# Boreas to ROS 2 bag converter research

Inspected 2026-11-05. Source files were read directly; temporary source checkouts and downloaded reference files were removed after research. No converter reference was cloned into the destination repository. The recommendations below are engineering judgments, not upstream guarantees.

## Decision

Build a small standalone `boreas_to_ros2bag` using native `rosbag2_py`, generated ROS 2 messages, `rclpy.serialization.serialize_message`, and MCAP/CDR. Reuse the **writer approach** demonstrated by WATonomous, with independently implemented Boreas parsing. A broad fork would retain nuScenes metadata, CAN, map, annotation, and dependency assumptions that Boreas does not need.

Ready Boreas converters exist, so this is a suitability decision rather than a claim that none exist. One lacks IMU support and a visible license; another was removed upstream and has a per-point timestamp scaling error. Neither provides the required combination of raw IMU semantics, explicit frame conventions, optional cameras, and reproducible native ROS 2 MCAP output.

### WATonomous details

The actual ROS 2 entry point is [convert_to_ros2bag.sh](https://github.com/WATonomous/nuscenes_to_ros2bag/blob/fdab70be80a7c6783c1810b4eba681685358913e/convert_to_ros2bag.sh), which launches `nuscenes2bag/convert_to_bag.py`. Its [writer setup](https://github.com/WATonomous/nuscenes_to_ros2bag/blob/fdab70be80a7c6783c1810b4eba681685358913e/nuscenes2bag/convert_to_bag.py#L26) is the appropriate pattern. Its [LiDAR parser](https://github.com/WATonomous/nuscenes_to_ros2bag/blob/fdab70be80a7c6783c1810b4eba681685358913e/nuscenes2bag/sensor_utils.py#L11) assumes five float32 fields and has no per-point time, unlike Boreas. Several keyframe records use an ego-pose bag timestamp instead of their own message timestamp; preserve actual acquisition timestamps in the new converter. The [Humble Dockerfile](https://github.com/WATonomous/nuscenes_to_ros2bag/blob/fdab70be80a7c6783c1810b4eba681685358913e/nuscenes2bag/Dockerfile) brings in nuScenes devkit, shapely, pypcd, map dependencies and other extras. [MIT license](https://github.com/WATonomous/nuscenes_to_ros2bag/blob/fdab70be80a7c6783c1810b4eba681685358913e/LICENSE).

Do not confuse that path with the legacy root `convert_to_mcap.py`: [RosmsgWriter.py](https://github.com/WATonomous/nuscenes_to_ros2bag/blob/fdab70be80a7c6783c1810b4eba681685358913e/RosmsgWriter.py) imports `rospy`, registers `ros1msg` schemas and `ros1` channel encoding, and invokes ROS 1 message serialization. Adapting such a path requires replacing generated messages, serialization and topic metadata, as well as the dataset reader; there is no benefit over the native writer approach.

### Foxglove details

Current [convert_to_mcap.py](https://github.com/foxglove/nuscenes2mcap/blob/0bcaab269379069b8a2df8ad4762f128c2552bb9/convert_to_mcap.py) uses Foxglove PointCloud, CompressedImage, CameraCalibration and FrameTransform types. Its [IMU/odometry channel declarations](https://github.com/foxglove/nuscenes2mcap/blob/0bcaab269379069b8a2df8ad4762f128c2552bb9/convert_to_mcap.py#L867) explicitly use JSON schema and JSON encoding. These are different from `sensor_msgs/msg/Imu` and `nav_msgs/msg/Odometry` serialized as CDR. [Dependencies](https://github.com/foxglove/nuscenes2mcap/blob/0bcaab269379069b8a2df8ad4762f128c2552bb9/pyproject.toml) include nuScenes devkit, Foxglove SDK, protobuf support, pypcd and a pinned Python 3.11 range. [MIT license](https://github.com/foxglove/nuscenes2mcap/blob/0bcaab269379069b8a2df8ad4762f128c2552bb9/LICENSE).

### Ready Boreas converters

The [vidhantsharma implementation](https://github.com/vidhantsharma/boreas_to_rosbag/blob/3434f4fbf2cfbdd0287f2903bbb7b1299d86de1e/scripts/boreas_to_rosbag.py) registers no Imu or CameraInfo topics, stores ring as FLOAT32, converts timestamps through epoch-valued floating point, and treats raw radar PNGs as ordinary BGR camera images. The entry point and duration are source constants. It appends GT records after sensor records rather than merging streams chronologically. Its README lists Humble, NumPy, pandas, OpenCV, tqdm, tf_transformations and native ROS dependencies. The inspected repository lists no LICENSE; do not copy its implementation without resolving reuse permission.

The [rsasaki historical implementation](https://github.com/rsasaki0109/lidar_localization_ros2/blob/9b6c1300066e5615a539dfaefa5dce167df98ed7/scripts/convert_boreas_sequence_to_rosbag2.py) correctly uses a UINT16 ring layout, permits time windows and strides, and rotates ENU linear velocity into the body frame. However, it [multiplies each point time by 1e-6](https://github.com/rsasaki0109/lidar_localization_ros2/blob/9b6c1300066e5615a539dfaefa5dce167df98ed7/scripts/convert_boreas_sequence_to_rosbag2.py#L336), inconsistent with the official loader's seconds convention. It defaults to gravity-removed `imu.csv`, requires GT, writes streams separately, and has no camera/radar/TF conversion. It was [removed on 2026-09-11](https://github.com/rsasaki0109/lidar_localization_ros2/commit/6825f055781f26c7542aa0fdd606476f869d1f58). Its repository uses [BSD-2-Clause](https://github.com/rsasaki0109/lidar_localization_ros2/blob/2becf541382eb42aae2855050d2715f725a72767/LICENSE).

### ROS 1 candidate search

An author-maintained [radar research tools list](https://github.com/dan11003/My-Radar-Research#tools) advertises a PyBoreas radar-to-rosbag tool and links to [dan11003/pyboreas](https://github.com/dan11003/pyboreas/tree/31bb69d33062f4ab78c48ae243040c0fed926286). The current recursive tree and both branch names were checked; no separately named ROS/rosbag converter was present. That advertised link is not evidence of a maintained, ready converter. The directly inspected WATonomous legacy ROS 1 serializer above is an adaptable serialization reference, but the existing native ROS 2 path avoids the entire migration layer. This search is not an exhaustive claim that no other ROS 1 converter exists.

## Boreas format decisions

The official [DATA_REFERENCE.md](https://github.com/utiasASRL/pyboreas/blob/8e100ff82ecd4992511da61b016398dbd230f205/DATA_REFERENCE.md) documents UTC microsecond filenames, exposure-center camera stamps, scan-center LiDAR stamps, six float32 LiDAR fields `[x,y,z,i,r,t]`, rectified PNG camera images, and the projection matrix `P_camera.txt`. Raw polar radar contains timestamp/encoder metadata in its first 11 columns. Ground truth is ENU, while raw IMU axes are x-backwards/y-left/z-down. These streams are asynchronous. `T_applanix_lidar` maps LiDAR coordinates into Applanix coordinates, not the reverse. Use those conventions without synchronizing samples artificially.

- **LiDAR timing:** the official [load_lidar](https://github.com/utiasASRL/pyboreas/blob/8e100ff82ecd4992511da61b016398dbd230f205/pyboreas/utils/utils.py#L17) adds the filename time in **seconds** directly to stored point `t`; therefore stored `t` is a relative offset in seconds, not microseconds. Keep signed offsets relative to the scan-center header, or consistently shift both the header and offsets if a consumer requires a scan-start convention. Do not put epoch seconds in FLOAT32. Preserve laser IDs as integer rings, ideally UINT16 after validation.
- **CSV timestamps:** `DATA_REFERENCE` describes microseconds, but the inspected historical native converter explicitly supports epoch seconds in `imu.csv`. Inspect the actual header and magnitude; parse decimal seconds exactly into integer nanoseconds, rather than float-rounding epoch timestamps. Keep filename microseconds as integers and multiply by 1000.
- **Processed IMU:** the maintainer [confirms rad/s, m/s², and gravity removed from imu.csv](https://github.com/utiasASRL/pyboreas/issues/24#issuecomment-1334042700). It is a postprocessed navigation solution, not untouched accelerometer output. Do not silently use it as a gravity-containing ROS IMU.
- **Raw IMU:** reorder CSV columns from `t,wz,wy,wx,az,ay,ax` into xyz vectors; keep the recorded rad/s and m/s² units. The maintainer [corrected the raw axes to x-back/y-left/z-down](https://github.com/utiasASRL/pyboreas/issues/44#issuecomment-2192454629). Applanix axes are x-right/y-forward/z-up, also documented in [odometry.py](https://github.com/utiasASRL/pyboreas/blob/8e100ff82ecd4992511da61b016398dbd230f205/pyboreas/utils/odometry.py#L54). Derived from those axes, `R_applanix_raw = [[0,-1,0],[-1,0,0],[0,0,-1]]`; raw-to-standard forward/left/up is `diag(-1,1,-1)`. These are orientation transformations, not measured translations.
- **Gravity/sign:** [REP 145 source](https://github.com/ros-infrastructure/rep/blob/master/rep-0145.rst#data-sources) defines ROS accelerometer data as specific force; stationary z-up should read approximately +g. A stationary raw z-down sample near -g is consistent after a proper rotation. Preserve raw specific force; do not subtract gravity again. Unknown orientation should have `orientation_covariance[0] = -1`; unknown reported covariances are zeros.
- **Unknown lever arm:** the official [Calib loader](https://github.com/utiasASRL/pyboreas/blob/8e100ff82ecd4992511da61b016398dbd230f205/pyboreas/data/calib.py) provides the Applanix-reference-to-LiDAR transform, but does not provide an original raw-IMU-origin-to-Applanix-reference translation. Do not claim that rotating raw acceleration also transfers it to the LiDAR origin. Explicitly document a co-location assumption or require a measured transform for acceleration-sensitive fusion. The new [IMU tutorial](https://github.com/utiasASRL/pyboreas/blob/8e100ff82ecd4992511da61b016398dbd230f205/pyboreas/tutorials/imu.ipynb) concerns Boreas-RT DMU/Aeva sensors and supplies no original raw IMU lever arm.

## Proposed implementation boundary

Use only NumPy plus installed ROS 2 Python/message packages for LiDAR, raw IMU and static transforms. Pillow can be optional for decoded raw camera images; alternatively, native `sensor_msgs/msg/CompressedImage` can carry PNG bytes without decoding, with dimensions read from PNG metadata and calibration from `P_camera.txt`. Keep camera conversion optional so LiDAR/IMU-only downloads work. Do not require ground truth to replay sensors; any GT export should be separate and optional. Use a stable timestamp merge of independent sensor iterators, one acquisition timestamp for the header and bag record, and a manifest recording topics, fields, input selection and frame assumptions. Validate the resulting file by reading it with native rosbag2 and checking decoded types, counts, timestamps, point-field values, IMU signs and TF connectivity.

The official devkit itself has a [BSD-3-Clause software license](https://github.com/utiasASRL/pyboreas/blob/8e100ff82ecd4992511da61b016398dbd230f205/LICENSE) and pulls OpenCV, matplotlib, pysteam and YAML in addition to NumPy through [setup.py](https://github.com/utiasASRL/pyboreas/blob/8e100ff82ecd4992511da61b016398dbd230f205/setup.py). Dataset licensing is recorded separately in [DATA_LICENSE.md](https://github.com/utiasASRL/pyboreas/blob/8e100ff82ecd4992511da61b016398dbd230f205/DATA_LICENSE.md); do not confuse software reuse permission with redistribution permission for recordings.
